# 更新インストールとデータ保持

[한국어](upgrade-validation.md) | [English](upgrade-validation.en.md) | 日本語

新規インストールと更新インストールを別々に実行します。テスト機器・アカウント・合成データを使い、実ユーザーデータを削除しません。

## 準備と順序

1. 実際の旧配布 artifact または同版を再現したビルドを用意します。再ビルドなら元の配布物と異なる限界を記録します。version/build、bundle ID、署名 team、keychain access group、App Group、保存 schema を比較します。
2. 旧アプリで合成データを作ります。レコードと関係、設定、下書き、テストログイン、オフラインデータ、該当すればテスト購入状態を含めます。秘密値ではなく ID・件数・関係・読み取り可否を期待値として残します。
3. 旧アプリを停止し、**削除・リセットせず**新アプリを上書きインストールします。同じ bundle ID と互換性のある署名・entitlement が必要です。データが保持されたか確認し、失敗を uninstall で回避しません。
4. 初回起動で store の読み込み、migration、関係、設定、session 復元を確認します。認証期限切れの正常な再認証とデータ損失を区別します。app/extension が App Group データを共有するなら両方の読み書きを検証します。
5. レコードを追加・編集・削除して再起動し、オフライン・オンライン復帰を確認します。初回処理が再実行されても migration や同期が重複しないか確認します。
6. 別の使い捨て環境で既存 test hook や fixture により migration 失敗・中断を再現します。元のテストデータのコピーを保存し、復旧・再試行・エラー UI を検証します。空の store への置換で損失を隠しません。

## 組み合わせと限界

- アプリ更新と機器 OS 更新を別々に記録します。新 simulator へのデータコピーは実機 OS 更新の検証ではありません。
- iOS 27 runtime に旧アプリを入れて上書きすればアプリ更新経路を検証できます。実際の OS 更新は利用可能なテスト機器で別途行います。未対応の runtime 更新コマンドを作りません。
- simulator ビルドと実機 artifact を混用しません。App Store アプリと開発署名アプリの keychain アクセス差だけで OS 回帰と断定しません。
- 旧 artifact がなければ schema fixture で部分検証し、全更新インストールは未実施とします。新コードのみで作った fixture では旧版互換性を証明できません。
- 新規インストールは別機器/コンテナで行います。downgrade は対応製品だけ別途検証し、旧バイナリが新 schema を読めるとは仮定しません。

## 完了の証拠

旧/新 artifact 識別子、OS build、インストール順序、データの前後比較、初回・再起動・復旧の結果を報告します。store が開くだけでデータ・関係・アカウント保持を合格にしません。これは一般的なアプリ更新手順で、iOS 27 の新しい必須要件ではありません。
