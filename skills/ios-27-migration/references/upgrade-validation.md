# 업데이트 설치와 데이터 보존 검증

한국어 | [English](upgrade-validation.en.md) | [日本語](upgrade-validation.ja.md)

클린 설치와 업데이트 설치를 별도 시나리오로 실행한다. 테스트 장치·계정·합성 데이터로 수행하고 실제 사용자 데이터를 삭제하지 않는다.

## 준비와 순서

1. 실제 이전 배포 버전 artifact 또는 동일 버전을 재현한 빌드를 확보한다. 재빌드했다면 원본 배포 artifact와 다르다는 한계를 기록한다. 버전/build, bundle ID, 서명 팀, keychain access group, App Group, 저장 스키마를 비교한다.
2. 이전 앱으로 합성 데이터를 만든다: 저장 항목과 관계, 설정, 입력 초안, 테스트 로그인, 오프라인 데이터, 앱에 있다면 테스트 구매 상태. 비밀 값 대신 ID·개수·관계·읽기 가능 여부로 기대 결과를 남긴다.
3. 이전 앱을 종료하고 **삭제·재설정 없이** 새 앱을 덮어 설치한다. 같은 bundle ID와 호환되는 서명·entitlement가 필요하다. 기존 데이터가 실제 유지됐는지 확인한다. 설치 실패를 uninstall로 우회하지 않는다.
4. 첫 실행에서 store 열기·마이그레이션·관계 보존·설정·세션 복원을 확인한다. 로그인 만료라면 정상적인 재인증인지 데이터 유실인지 구별한다. 앱/extension이 App Group 데이터를 함께 쓰면 양쪽 읽기·쓰기를 검증한다.
5. 새 항목 추가·수정·삭제 후 재실행하고 오프라인·온라인 복귀를 확인한다. 첫 실행이 반복돼도 마이그레이션이나 동기화가 중복 적용되지 않는지 확인한다.
6. 별도의 일회용 환경에서 migration 실패·중단을 기존 test hook이나 fixture로 재현한다. 원본 테스트 데이터 사본을 보존하고 복구·재시도·오류 UI를 검증한다. 실패하면 빈 store로 교체하는 fallback으로 데이터 손실을 숨기지 않는다.

## 테스트 조합과 한계

- 앱 업데이트와 기기 OS 업데이트를 따로 기록한다. 새 simulator에 데이터를 복사한 것은 실제 기기 OS 업데이트 검증과 같지 않다.
- 이전 앱을 iOS 27 runtime에 설치한 뒤 덮어 설치하면 앱 업데이트 경로를 검증할 수 있다. 실제 OS 업데이트 경로는 가능한 테스트 장치에서 별도로 수행한다. 미지원 runtime 업그레이드 명령을 만들어내지 않는다.
- simulator 빌드와 실기기 artifact를 혼용하지 않는다. App Store 앱과 개발 서명 앱의 keychain 접근 차이는 OS 회귀로 단정하지 않는다.
- 이전 artifact가 없으면 schema fixture 테스트로 가능한 부분을 확인하고 전체 업데이트 설치는 미실시로 남긴다. 새 코드가 만든 fixture만으로 이전 버전 호환성을 입증하지 않는다.
- 클린 설치는 별도 장치/컨테이너에서 실행한다. downgrade는 지원하는 제품에 한해 별도 검증하고 새 스키마가 구 바이너리에서 읽힌다고 가정하지 않는다.

## 완료 증거

이전/새 artifact 식별자, OS build, 설치 순서, 테스트 데이터의 변경 전후 비교, 첫 실행·재실행·실패 복구 결과를 보고한다. store가 열리는 것만으로 데이터·관계·계정 보존을 통과 처리하지 않는다. 이 절차는 일반적인 앱 업데이트 검증이며 iOS 27의 신규 필수 요구사항이 아니다.
